# Pebble API - Product Requirements Document

## 1. 서비스 목적

### 1.1 초기 목적

Pebble은 개발자가 자신의 기술 지식, 개발 경험 및 프로젝트를 기록하고 공유할 수 있는 개발자 커뮤니티형 블로그 및 포트폴리오 서비스이다.

MVP에서는 다음을 핵심 목적으로 한다.

- 개발자의 기술 블로그 게시글 작성 및 공유
- 개발 프로젝트의 소개 및 공유
- 기술 콘텐츠와 프로젝트의 탐색
- 사용자 간 댓글 및 좋아요를 통한 콘텐츠 상호작용
- 사용자가 자신의 콘텐츠를 직접 관리할 수 있는 환경 제공
- 관리자의 콘텐츠 검토 및 서비스 운영

### 1.2 장기 목적

초기에는 개발자 중심의 콘텐츠 공유 서비스로 시작하지만, 향후 다양한 사용자가 참여할 수 있는 플랫폼으로 확장할 수 있는 기반을 마련한다.

장기적으로 다음과 같은 기능 확장을 고려한다.

- 사용자 콘텐츠의 다양화
- 댓글 및 사용자 상호작용 기능 고도화
- 사용자 프로필 및 활동 정보 확장
- 다양한 소셜 로그인 지원
- 프로젝트 공유 및 협업 기능
- 콘텐츠 검색 및 추천 기능 고도화
- 관리자 운영 및 검수 기능 고도화

단, MVP에서는 실제 사용자 요구사항에 필요한 기능을 우선 구현하며 미래 확장을 위한 기능을 과도하게 선구현하지 않는다.

## 2. 제품 개요

Pebble은 개발자가 기술 콘텐츠와 프로젝트를 직접 작성하고 다른 사용자가 이를 탐색할 수 있는 서비스이다.

Pebble에서는 사용자가 작성하는 주요 콘텐츠를 `Post`와 `Project`로 구분한다.

- `Post`: 기술 지식과 개발 경험을 공유하는 기술 블로그 게시글
- `Project`: 개발 프로젝트와 포트폴리오 정보를 소개하는 프로젝트 콘텐츠

`Post`와 `Project`는 서로 다른 목적과 데이터 구조, 화면 및 검색 경험을 가지므로 별도의 Feature로 관리한다.

### 2.1 Post

개발 과정에서 얻은 지식, 문제 해결 과정, 기술 설명 및 경험을 공유하기 위한 일반적인 기술 블로그 콘텐츠이다.

### 2.2 Project

개발자가 직접 제작한 프로젝트를 포트폴리오 형태로 소개하고 다른 사용자가 프로젝트를 탐색하거나 GitHub 및 배포 환경으로 이동하여 직접 확인할 수 있도록 하는 콘텐츠이다.

Post와 Project는 모두 사용자 콘텐츠이지만 목적과 표현 방식이 다르므로 서로 다른 화면 구성과 검색 경험을 제공한다.

## 3. 사용자 유형

### 3.1 Guest

로그인하지 않은 방문자이다.

Pebble의 공개 콘텐츠를 자유롭게 탐색하고 읽을 수 있지만 사용자 참여 기능은 제한된다.

#### 주요 권한

- 공개 Post 조회
- 공개 Project 조회
- 공개 블로그 게시판 및 게시글 목록 조회
- 카테고리 및 기술 태그 조회
- Post 검색
- Project 검색
- 로그인

#### 제한 기능

- Post 작성
- Project 작성
- 댓글 작성
- 좋아요
- 기타 회원 전용 상호작용

---

### 3.2 USER

Naver 로그인을 통해 Pebble을 이용하는 일반 사용자이다.

USER는 콘텐츠의 소비자이면서 동시에 콘텐츠 생산자이다.

#### 주요 권한

- 공개 Post 조회
- 공개 Project 조회
- Post 검색
- Project 검색
- Post 작성 및 관리
- 개인 블로그 게시판 생성 및 관리
- Post를 개인 블로그 게시판에 배치 및 게시판별 공개 글 탐색
- Project 작성 및 관리
- 댓글 작성
- 댓글 관리
- 좋아요
- 본인 콘텐츠 관리
- 본인 계정 정보 조회

USER는 자신이 작성한 콘텐츠만 직접 수정 및 관리할 수 있다.

---

### 3.3 MANAGER

Pebble의 서비스 운영과 콘텐츠 검수를 담당하는 관리자이다.

MANAGER의 주요 역할은 콘텐츠를 직접 생산하는 것이 아니라 **사용자가 작성한 콘텐츠와 서비스 이용 상태를 관리하는 것**이다.

#### 주요 권한

- 사용자 콘텐츠 검토
- 콘텐츠 차단 및 차단 해제
- 콘텐츠 강제 삭제
- 댓글 관리
- 공통 카테고리 및 기술 태그 관리
- 사용자 상태 관리
- 신고 및 운영 요청 처리

MANAGER가 일반 사용자의 콘텐츠를 수정하여 대신 작성하는 것을 기본 운영 방식으로 사용하지 않는다.

서비스 운영상 공지나 관리자 작성 콘텐츠가 필요한 경우 일반 사용자 콘텐츠와 분리된 별도의 운영 콘텐츠 기능을 고려한다.

---

### 3.4 MASTER

Pebble의 최고 관리자이다.

MASTER는 관리자 계정과 운영 권한을 관리한다.

#### 주요 권한

- MANAGER 계정 생성
- MANAGER 계정 활성화 및 비활성화
- 관리자 권한 관리
- 관리자 계정 상태 관리
- MANAGER의 모든 운영 기능 사용

MASTER 역시 일반 사용자의 콘텐츠를 직접 작성하거나 대신 관리하는 것을 주요 역할로 하지 않는다.

---

## 4. 콘텐츠 구조

Pebble의 콘텐츠는 Post와 Project라는 두 가지 유형으로 구성한다.

### 4.1 콘텐츠 공통 개념

Post와 Project는 다음과 같은 공통적인 특성을 가진다.

- 사용자가 작성한다.
- 작성자를 가진다.
- 공개 상태를 가진다.
- 작성 및 수정이 가능하다.
- 다른 사용자가 조회할 수 있다.
- 관리자에 의해 검토될 수 있다.
- 관리자는 작성자의 공개 상태와 별도로 콘텐츠를 차단하거나 차단 해제할 수 있다.
- 관리자에 의해 강제 삭제될 수 있다.

관리자 차단은 작성자의 공개 상태와 독립적으로 관리한다. 차단된 콘텐츠는 공개 상태가 PUBLIC이어도 일반 사용자에게 노출하지 않는다.

다만 Post와 Project는 콘텐츠의 목적과 사용자 경험이 다르므로 동일한 화면이나 검색 경험으로 통합하지 않는다.

서비스 공통 카테고리와 개인 블로그 게시판은 별개의 기능이다. 공통 카테고리는 콘텐츠 탐색을 위한 분류이며, 개인 블로그 게시판은 사용자가 자신의 Post를 정리하기 위한 구조다.

---

## 5. Post

Post는 개발자가 기술 지식과 개발 경험을 공유하기 위한 일반적인 기술 블로그 게시글이다.

### 5.1 주요 목적

- 기술 개념 설명
- 개발 과정 기록
- 문제 해결 과정 공유
- 개발 경험 및 노하우 공유
- 특정 기술에 대한 튜토리얼 작성
- 프로젝트 개발 과정 기록

### 5.2 작성 및 관리

USER는 자신의 Post를 관리할 수 있다.

- Post 작성
- Post 조회
- Post 수정
- Post 삭제
- 공개/비공개 상태 변경
- 카테고리 지정
- 기술 태그 지정
- 개인 블로그 게시판 지정
- 썸네일 지정 (후속)
- 관련 Project 연결 (후속)
- 본인 블로그 목록 순서 변경

현재 Post API는 프로필 설정을 마친 ACTIVE 회원의 작성·수정·논리 삭제를 제공한다. 블로그 주소는 고정된 공개 handle과 선택 입력한 Post slug로 구성하며, slug가 없으면 작성자별 1부터 증가하는 글 번호를 사용한다. slug는 영문 소문자·숫자·단어 사이 하이픈만 허용하고 한글은 받지 않는다. 같은 작성자의 중복 입력에는 숫자 접미사를 붙인다. 생성 후 slug와 글 번호는 변경하지 않으며 논리 삭제 뒤에도 재사용하지 않는다. 본인 블로그의 미삭제 Post는 0부터 시작하는 수동 순서로 보고, 전체 공개 목록은 최초 공개 시각 내림차순으로 본다.

개인 Board 관리와 Post Board·Project 지정 및 공개 Post 기본 문자열 검색을 제공한다. Project는 기본 CRUD와 공개 목록·상세·검색, 회원별 공개·본인 목록, 기술 Tag·주요 기능·외부 링크 관리를 제공한다. Project 삭제 시 연결 글은 보존하고 연결만 해제한다. Post·Project 좋아요 등록·취소 및 공개 집계와 요청 회원의 likedByMe, 공개·비밀 댓글과 본인 댓글 관리를 제공한다. 썸네일·미디어 및 관리자 콘텐츠 운영은 후속 기능이다. Post의 projectId는 연결 ID 또는 null이며 thumbnailUrl은 현재 null이다.

향후 Post 썸네일과 Project 이미지·스크린샷은 정적 JPEG(.jpg, .jpeg), PNG, WebP 입력만 허용한다. 제공될 때 서버는 실제 파일 형식과 크기를 검증한 뒤 긴 변 2,560 px 화면 표시 이미지와 480 px 썸네일로 축소하고 WebP lossy quality 82로 변환한다. 입력은 최대 10 MiB, 20,000,000 픽셀, 가로·세로 각각 8,000 px로 제한한다. EXIF 등 불필요한 메타데이터를 제거하고 WebP 파생본만 저장하며 원본은 보관하지 않는다. 작은 글자나 얇은 선이 많은 PNG는 변환 후 경계가 다소 부드러워지거나 압축 흔적이 보일 수 있다. 비공개 R2 이미지 URL은 권한 확인 후 15분간 유효하다. Post 썸네일 API는 아직 제공하지 않으며 상세 계약은 `API.md`를 따른다.

사용자는 다른 사용자의 Post를 수정하거나 삭제할 수 없다.

관리자는 운영 목적으로 사용자의 Post를 차단하거나 강제 삭제할 수 있다. 차단은 작성자의 공개 상태를 변경하지 않으며, 작성자는 차단을 해제할 수 없다. 해당 관리자 API는 현재 구현되어 있지 않다.

## 6. Post 본문 및 코드 블록

기술 블로그의 핵심 기능으로 **구조화된 코드 블록 작성 기능**을 제공한다.

### 6.1 코드 블록

작성자는 본문 안에 일반 텍스트와 별도로 코드 블록을 삽입할 수 있어야 한다.

코드 블록은 일반 본문과 시각적으로 구분되며, 선택한 프로그래밍 언어에 맞는 문법 강조를 제공할 수 있어야 한다.

### 6.2 지원 언어

MVP에서는 개발 콘텐츠에서 자주 사용되는 언어 및 문법을 우선 지원한다.

기본 지원 대상:

- Java
- JavaScript
- TypeScript
- Python
- HTML
- CSS
- SQL
- JSON
- YAML
- Markdown
- Bash / Shell

향후 실제 사용 빈도에 따라 지원 언어를 추가할 수 있다.

### 6.3 코드 블록 요구사항

각 코드 블록은 다음 정보를 가질 수 있어야 한다.

- 코드 내용
- 언어
- 코드 표시 순서
- 필요에 따라 제목 또는 설명

예:

```text
[본문]

Spring Security 설정을 다음과 같이 구성한다.

┌─────────────────────────────────────┐
│ Java                         Copy   │
├─────────────────────────────────────┤
│ @Configuration                      │
│ @EnableWebSecurity                   │
│ public class SecurityConfig {        │
│     ...                              │
│ }                                    │
└─────────────────────────────────────┘

[본문 계속]
```

코드 블록의 실제 저장 형식과 API 데이터 구조는 `API.md` 및 `DB.md`에서 정의한다.

## 7. Post 카테고리 및 기술 태그

카테고리는 Post의 주요 주제를 표현하고, 기술 태그는 Post와 Project에서 사용하는 구체적인 언어와 기술을 표현한다.

예:

```text
카테고리: Backend
기술 태그: Java, Spring Boot, JPA
```

카테고리는 `Backend`, `Frontend`, `Database`, `DevOps`, `Architecture`처럼 안정적인 주제 분류를 사용한다. Java, JavaScript, HTML, CSS, Spring, PostgreSQL처럼 구체적인 언어와 기술은 카테고리가 아니라 기술 태그로 관리한다.

### 7.1 카테고리 요구사항

- 서비스 공통 카테고리는 관리자만 생성, 수정, 비활성화할 수 있다.
- 카테고리는 상위 주제와 하위 주제로 최대 2단계까지 구성할 수 있다.
- Post는 0개 또는 1개의 최하위 카테고리에 지정할 수 있다. 하위 카테고리가 있는 상위 카테고리는 탐색을 위한 그룹으로 사용한다.
- Post가 하위 카테고리에 지정되면 상위 카테고리에서도 해당 Post를 탐색할 수 있다.
- 비활성 카테고리는 신규 선택 목록에서 제외한다. 이미 지정된 카테고리는 기존 Post에서 계속 표시하며, 공개 Post는 비활성 카테고리로도 계속 탐색할 수 있다.
- 카테고리의 상세 구조와 제약조건은 `DB.md`에서 정의한다.

### 7.2 기술 태그 요구사항

- 기술 태그는 Java, Spring, JavaScript, React, HTML, CSS, PostgreSQL 등 기술과 언어의 표준 이름을 관리한다.
- Post에는 0개 이상의 기술 태그를 지정할 수 있다.
- Project의 기술 스택도 같은 기술 태그 목록에서 선택한다.
- MVP에서 일반 사용자는 기존 기술 태그를 선택하며, 새 기술 태그 등록과 비활성화는 관리자가 수행한다.
- 하나의 기술 태그를 Post와 Project에서 함께 사용할 수 있다.
- 비활성 태그는 신규 선택 목록에서 제외한다. 이미 지정된 태그는 기존 Post·Project에서 계속 표시하며, 공개 콘텐츠는 비활성 태그로도 계속 탐색할 수 있다.
- 태그의 상세 구조와 제약조건은 `DB.md`에서 정의한다.

---

## 8. Project

Project는 개발자가 제작한 프로젝트를 다른 개발자에게 소개하고 공유하기 위한 포트폴리오형 콘텐츠이다.

일반적인 기술 블로그 Post와 목적이 다르므로 독립적인 레이아웃과 탐색 경험을 제공한다.

### 8.1 주요 목적

- 개인이 작성하는 프로젝트 포트폴리오 소개
- 프로젝트 기술 스택 소개
- 프로젝트 아키텍처 설명
- 프로젝트 개발 과정 설명
- GitHub 저장소 공유
- 배포 환경 공유
- 프로젝트 실행 방법 제공
- 프로젝트 결과물 및 스크린샷 공유

### 8.2 주요 정보

Project는 다음과 같은 정보를 포함할 수 있다.

- 프로젝트명
- 프로젝트 소개
- 프로젝트 상세 설명
- 프로젝트 기간
- 프로젝트 상태
- 기술 스택
- GitHub URL
- 배포 URL
- 실행 방법
- 다운로드 정보
- 대표 이미지
- 프로젝트 스크린샷
- 아키텍처 설명
- 주요 기능 목록: 기능명과 설명을 각각의 항목으로 입력하고 순서를 정한다.

Project의 전체적인 배경과 서술은 프로젝트 소개/상세 설명에 작성한다. 주요 기능은 예를 들어 `OAuth 로그인 — Naver 인증과 JWT 발급`, `게시글 작성 — 텍스트·코드 블록 편집`처럼 항목별로 별도 입력한다. 이를 통해 기능 항목을 독립적으로 추가·수정·삭제·재정렬하고 상세 화면에 목록으로 표시한다.

Project 진행 상태는 `IN_PROGRESS`(진행 중) 또는 `COMPLETED`(완료) 중 하나를 작성자가 지정한다. MVP에서는 아직 시작하지 않은 예정 상태와 중단 상태를 별도 관리하지 않는다.

### 8.3 Project 관리

USER는 자신이 작성한 Project를 관리할 수 있다.

- Project 작성
- Project 조회
- Project 수정
- Project 삭제
- 공개/비공개 상태 변경
- 기술 스택 관리
- GitHub URL 관리
- 배포 URL 관리
- 실행 및 다운로드 정보 관리

관리자는 운영 목적으로 Project를 차단하거나 강제 삭제할 수 있다. 차단은 작성자의 공개 상태를 변경하지 않으며, 작성자는 차단을 해제할 수 없다.

MVP의 Project는 한 명의 Pebble 사용자가 소유하고 작성하는 개인 콘텐츠다. 팀 프로젝트 참여자 연결, 공동 편집 및 참여자 프로필 표시는 MVP 범위에서 제외한다. 사용자는 자신이 작성한 Project에 각자 관리하는 외부 링크를 등록한다.

## 10. Post와 Project의 관계

`Post`와 `Project`는 사용자가 작성하는 서로 다른 콘텐츠 유형이며, 각각 독립적인 Feature로 관리한다.

`Project`를 `Post`의 특정 카테고리로 취급하지 않는다.

그 이유는 다음과 같다.

- Project는 일반 Post와 목적이 다르다.
- Project는 별도의 상세 레이아웃을 가진다.
- Project는 별도의 검색 경험을 제공한다.
- Project는 GitHub 및 배포 환경과 연결된다.
- Project는 실행 및 다운로드 정보를 제공할 수 있다.
- Project는 포트폴리오로서 독립적으로 탐색될 수 있다.

다만 Project와 관련된 기술 기록을 Post로 작성할 수 있으며, 필요에 따라 Post와 Project를 연결할 수 있다.

하나의 Project에는 여러 Post를 연결할 수 있다. 하나의 Post는 단독으로 둘 수 있고, 연결하는 경우 Project 하나에만 연결한다. MVP에서는 사용자가 자신이 소유한 Project에 자신의 Post를 연결한다.

예:

```text
Project: Pebble

관련 Post
├── Spring Security 인증 구조 구현
├── PostgreSQL 설계 과정
├── Redis Refresh Token 관리
└── GitHub Actions 배포 구성
```

구체적인 관계 모델은 `DB.md`에서 정의한다.

## 11. 콘텐츠 공개 상태

Post와 Project는 작성자가 관리하는 공개 상태와 관리자가 관리하는 차단 상태를 별도로 가진다.

### 11.1 PUBLIC

공개 상태의 콘텐츠이다.

- Guest가 조회할 수 있다.
- USER가 조회할 수 있다.
- 검색 결과에 포함될 수 있다.
- 좋아요 및 댓글 등의 회원 기능을 사용할 수 있다.
- 단, 관리자가 차단한 콘텐츠는 일반 사용자에게 노출하지 않으며 일반 검색과 상호작용 대상에서 제외한다.

### 11.2 HIDDEN

작성자가 비공개한 콘텐츠이다. 관리자의 차단은 별도의 차단 상태로 관리한다.

- Guest가 조회할 수 없다.
- 일반 USER가 조회할 수 없다.
- 일반 검색 결과에 포함되지 않는다.
- 작성자는 자신의 콘텐츠를 관리 목적으로 확인할 수 있다.
- 관리자는 운영 목적으로 확인할 수 있다.

작성자는 자신의 HIDDEN 콘텐츠를 다시 PUBLIC으로 변경할 수 있다. 관리자 차단 상태가 켜져 있으면 PUBLIC으로 변경해도 일반 사용자에게 노출되지 않는다.

### 11.3 관리자 차단

관리자는 Post 또는 Project의 차단 상태를 공개 상태와 별도로 설정할 수 있다.

- 차단 여부는 콘텐츠의 공개 상태와 독립적이다.
- 차단된 콘텐츠는 Guest와 일반 USER의 상세 조회, 목록 및 검색에서 제외한다. 공개 댓글과 좋아요는 일반 사용자에게 노출하거나 새로 등록할 수 없고, 좋아요 집계에서도 제외한다.
- 비밀 댓글은 대상 콘텐츠가 차단되어도 댓글 작성자, 콘텐츠 작성자, 권한이 있는 관리자만 조회할 수 있다.
- 작성자는 차단 여부를 조회할 수 있지만 변경할 수 없다.
- MANAGER와 MASTER는 차단을 설정하거나 해제할 수 있다.
- 차단 해제는 작성자의 공개 상태를 바꾸지 않는다. HIDDEN 콘텐츠는 차단 해제 후에도 일반 사용자에게 공개되지 않는다.

### 11.4 DELETED

삭제 처리된 콘텐츠이다.

삭제된 콘텐츠는 일반적인 사용자 조회 및 검색 대상에서 제외한다.

실제 데이터의 보존 여부와 삭제 처리 방식은 `DB.md`에서 정의한다.

## 12. 사용자 콘텐츠 관리

USER는 자신이 작성한 콘텐츠에 대한 관리 권한을 가진다.

### 12.1 본인 콘텐츠

사용자는 다음 콘텐츠를 직접 관리할 수 있다.

- 자신이 작성한 Post
- 자신이 작성한 Project
- 자신이 작성한 댓글

### 12.2 다른 사용자의 콘텐츠

사용자는 다른 사용자의 콘텐츠를 임의로 수정하거나 삭제할 수 없다.

다른 사용자의 콘텐츠에 문제가 있다고 판단되는 경우 향후 신고 기능을 통해 관리자에게 검토를 요청할 수 있다.

### 12.3 개인 블로그 게시판

USER는 자신의 Post를 정리하기 위해 개인 블로그 게시판을 만들고 관리할 수 있다.

- ACTIVE USER는 프로필 설정 완료와 관계없이 Board를 생성·수정·삭제할 수 있다.
- 게시판을 최대 3단계까지 계층으로 구성하고 이름·부모·displayOrder를 관리한다.
- 이름은 공백이 아니며 최대 50 유니코드 코드 포인트다. 같은 부모 아래 삭제되지 않은 Board와 대소문자까지 같은 이름을 중복할 수 없고, 삭제한 이름은 재사용할 수 있다.
- displayOrder는 0 이상의 정렬 키다. 같은 순서는 숫자 ID 오름차순으로 보여주며 순서 변경 때 다른 Board를 자동으로 이동하지 않는다.
- 자신의 Post를 0개 또는 1개의 개인 게시판에 배치한다. Board는 서비스 공통 Category와 별도로 관리한다.
- 게시판 삭제 시 연결된 Post를 삭제하지 않고 미분류 상태로 둔다. 논리 삭제된 Post의 Board 연결도 함께 제거한다.
- 미삭제 하위 게시판이 남아 있는 게시판은 하위 게시판을 먼저 이동하거나 삭제해야 삭제할 수 있다.
- 공개 Board 트리에서 parentId는 노출하지 않는다. Board별 Post 탐색은 해당 Board에 직접 배치된 공개·비차단 Post만 반환하고 하위 Board의 Post는 포함하지 않으며 Category·Tag 필터는 제공하지 않는다. 전역 Post 목록에도 Board 필터는 제공하지 않는다.
- 게시판은 Post의 공개 상태를 변경하거나 우회하지 않는다. Post 작성·수정에는 기존 프로필 완료 요건이 적용된다.

## 13. 댓글

댓글은 회원 간 콘텐츠 상호작용을 위한 기능이다.

### 13.1 권한

- Guest: 공개 콘텐츠의 공개 댓글 조회 가능
- USER: 공개 댓글 또는 비밀 댓글 작성, 본인 댓글 조회·수정·삭제
- 콘텐츠 작성자: 자신이 소유한 콘텐츠에 달린 비밀 댓글 조회
- MANAGER: 운영 목적의 댓글 관리
- MASTER: MANAGER의 댓글 관리 기능을 포함한 전체 운영 기능

비밀 댓글은 댓글 작성자, 대상 콘텐츠 작성자, 권한이 있는 관리자만 조회할 수 있다. 그 외 회원과 Guest에게는 노출하지 않는다. 댓글의 공개 범위는 대상 콘텐츠의 공개 상태와 별도로 서버에서 검증한다.

### 13.2 기본 요구사항

- 공개 콘텐츠의 댓글 조회
- 공개 댓글 및 비밀 댓글 작성
- 본인 댓글 수정
- 본인 댓글 삭제
- 관리자 댓글 관리

대댓글은 MVP에서 필요성이 확인된 경우 추가한다.

현재 일반 댓글 작성·조회·본인 수정·삭제를 제공하며 관리자 인증·운영 댓글 관리는 후속 범위다. ACTIVE USER는 프로필 완료 없이 댓글을 작성·관리한다. 댓글 삭제는 본문을 제거하고 일반 조회에서 숨긴다. 부모의 숨김·차단 상태에서도 본인 댓글 수정·삭제와 본인 SECRET 단일 조회는 가능하지만 부모가 삭제되거나 소유자가 탈퇴 대기이면 일반 댓글 영역은 제공하지 않는다. 탈퇴 대기 댓글 작성자의 댓글은 숨기며 정지 작성자의 기존 공개 댓글은 유지한다.

## 14. 좋아요

좋아요는 회원 간 콘텐츠 상호작용을 위한 기능이다.

### 14.1 권한

- Guest: 좋아요 불가
- USER: 좋아요 가능
- MANAGER / MASTER: 좋아요를 등록하거나 취소할 수 없다. 콘텐츠 운영 권한은 별도로 가진다.

### 14.2 기본 요구사항

- Post 좋아요
- Project 좋아요
- 좋아요 취소
- 콘텐츠별 좋아요 수 조회

동일한 사용자가 동일 콘텐츠에 중복으로 좋아요를 등록하지 않도록 한다.

등록·취소는 ACTIVE USER가 공개·미차단·미삭제 콘텐츠에만 수행한다. 프로필 최초 설정은 상호작용의 필수 조건이 아니다. 취소는 논리 삭제하고 재등록은 새 행을 추가하며 중복 요청은 같은 결과를 유지한다. 숨김·차단·논리 삭제 시 좋아요 이력은 보존하고 일반 집계에서 숨긴다. 탈퇴 대기 회원의 좋아요는 집계에서 제외하고 정지 회원의 기존 좋아요는 유지한다.

## 15. 검색

Pebble은 Post와 Project의 목적이 다르기 때문에 검색 경험도 분리한다.

### 15.1 Post 검색

기술 블로그 콘텐츠를 대상으로 검색한다.

검색 대상:

- 제목
- 본문
- 카테고리
- 태그

현재 Post 검색은 제목, 본문 블록 content·title, 연결 Category와 상위 Category 이름, Tag 이름의 대소문자를 구분하지 않는 부분 문자열 검색을 제공한다. 앞뒤 공백을 제거한 검색어는 1~200 유니코드 코드 포인트이며 %, _, 역슬래시는 문자 그대로 검색한다. 검색어와 Category·Tag·작성자 필터를 함께 적용할 수 있다. 공개 필터를 적용한 뒤 publishedAt 기본 내림차순으로 페이징하며, 여러 블록·태그가 일치해도 같은 글은 한 번만 반환한다. summary·slug 검색과 관련도 정렬은 현재 제공하지 않는다.

---

### 15.2 Project 검색

개발 프로젝트를 대상으로 검색한다.

검색 대상의 예:

- 프로젝트명
- 프로젝트 소개
- 기술 스택
- 프로젝트 설명
- 관련 태그

Project 검색은 기술 스택이나 프로젝트 분야 등 Project 특성에 맞는 검색 조건을 추가할 수 있다.

---

### 15.3 검색 범위

일반 사용자는 공개된 콘텐츠만 검색할 수 있다.

HIDDEN, 관리자 차단 또는 삭제 처리된 콘텐츠는 일반 검색 결과에 포함하지 않는다.

구체적인 검색 구현 방식은 `DB.md` 및 `ARCHITECTURE.md`에서 정의한다.

## 16. 관리자 운영 및 검수

관리자의 핵심 역할은 사용자 콘텐츠의 생산이 아니라 **서비스 운영과 콘텐츠 검수**이다.

### 16.1 MANAGER

MANAGER는 다음과 같은 운영 기능을 수행한다.

#### 콘텐츠 검수

- 사용자 Post 조회
- 사용자 Project 조회
- 콘텐츠 차단 및 차단 해제
- 콘텐츠 강제 삭제

#### 분류 체계 관리

- Post 공통 카테고리 관리
- 기술 태그 목록 관리

#### 댓글 관리

- 부적절한 댓글 관리
- 댓글 삭제
- 운영 정책에 따른 댓글 제한

#### 사용자 관리

- 사용자 목록 조회
- 사용자 상태 조회
- 사용자 계정 정지
- 사용자 계정 활성화

#### 신고 및 운영

향후 신고 기능이 추가되는 경우 신고된 콘텐츠와 사용자를 검토하고 처리한다.

---

### 16.2 MASTER

MASTER는 관리자 시스템을 관리한다.

- MANAGER 계정 생성
- MANAGER 계정 활성화
- MANAGER 계정 비활성화
- 관리자 권한 관리
- 관리자 상태 관리
- MANAGER 운영 기능 사용

## 17. 공지 및 운영 콘텐츠

관리자가 서비스 운영을 위해 직접 작성하는 콘텐츠가 필요한 경우 일반 사용자 Post와 분리한다.

예:

```text
Notice
├── 서비스 업데이트 안내
├── 점검 안내
└── 운영 정책 안내
```

공지 기능은 일반적인 사용자 기술 블로그 Post와 동일한 콘텐츠로 취급하지 않는다.

MVP에서 별도의 공지 기능이 필요하지 않다면 구현하지 않는다.

## 18. 회원 및 인증 정책

### 18.1 일반 사용자

- 일반 사용자는 Naver를 통해 가입 및 로그인한다.
- 첫 로그인에서 Naver 별명을 기본 닉네임으로 부여하고 중복이면 숫자 접미사를 붙인다. 사용자는 최초 설정에서 블로그명과 공개 아이디를 정하며 닉네임도 선택적으로 바꿀 수 있다.
- 블로그명(한글·영문, 최대 100자)·닉네임(한글·영문, 최대 30자)·공개 아이디는 각각 고유하다. 블로그명과 닉네임은 최초 설정/마지막 실제 변경 후 필드별 7일이 지나야 변경할 수 있다. 공개 아이디는 영문·숫자·하이픈 3~30자로 최초 확정 후 영구 고정한다.
- 공개 아이디는 로그인 자격 증명이 아니라 블로그 주소용이며, 내부 회원 TSID 및 Naver 식별자와 구분한다. 재로그인이 사용자의 프로필을 덮어쓰지 않는다.
- 일반 사용자는 별도의 ID/PW 회원가입을 사용할 수 없다.
- 로그인하지 않은 방문자는 공개 콘텐츠를 조회할 수 있다.
- 회원은 댓글, 좋아요 등의 상호작용 기능을 사용할 수 있다.
- 회원은 자신의 Post와 Project를 작성하고 관리할 수 있다.

### 18.2 관리자

- 관리자는 일반 사용자와 별도의 관리자 계정 체계를 사용한다.
- 관리자 계정은 일반 사용자 가입 절차를 통해 생성하지 않는다.
- 관리자 권한은 MANAGER와 MASTER로 구분한다.
- MASTER만 MANAGER 계정을 관리할 수 있다.

### 18.3 회원 탈퇴

- 탈퇴 요청 즉시 로그인을 차단하고 7일간 탈퇴 예약 상태를 둔다. 이 기간 동안 계정과 기존 Refresh Token 세션을 사용할 수 없고 공개 프로필과 콘텐츠도 일반 조회·검색에서 숨긴다.
- 회원은 7일 안에 Naver 재인증으로 탈퇴 예약을 취소할 수 있다. 취소하면 계정과 콘텐츠 상태를 복원하지만 기존 세션은 되살리지 않으며 다시 로그인해야 한다.
- 7일 안에 취소하지 않으면 회원, OAuth 연결, Post, Project, 댓글, 좋아요, Board 및 R2 미디어를 운영 데이터베이스와 저장소에서 물리 삭제한다. 결제·주문 데이터는 MVP에 없으므로 탈퇴 뒤 별도로 유지할 거래 데이터는 두지 않는다.
- 관리자 접속기록은 회원 콘텐츠와 분리해 SECURITY.md의 보유기간으로 보관한다. 개인정보가 포함된 백업은 별도 접근 통제하고 정해진 백업 만료 시점에 파기한다. 복원 전에는 탈퇴 완료 기록을 다시 적용한다.

인증 및 접근 제어의 상세 구현은 `SECURITY.md`에서 정의한다.

## 19. 사용자 상태 관리

서비스 운영을 위해 일반 사용자 계정의 상태를 관리할 수 있어야 한다.

기본 상태:

| 상태 | 설명 |
|---|---|
| `ACTIVE` | 정상적으로 서비스를 이용할 수 있는 상태 |
| `SUSPENDED` | 관리자에 의해 서비스 이용이 제한된 상태 |
| `WITHDRAWAL_PENDING` | 탈퇴 요청 후 7일 유예 중. 로그인과 회원 기능은 차단되며 콘텐츠는 숨김 |

유예 기간이 끝나면 회원과 소유 데이터를 물리 삭제하므로 `WITHDRAWN` 상태의 회원 레코드는 남기지 않는다. 관리자 계정 역시 별도의 활성화/비활성화 상태를 가질 수 있다.

구체적인 상태 전이 규칙은 `SECURITY.md` 및 `DB.md`에서 정의한다.

## 24. MVP 완료 기준

### Guest

- 공개 사용자의 블로그 게시판 구조를 조회할 수 있다.
- 게시판별 공개 Post만 조회할 수 있다.
- 공개 Post를 조회할 수 있다.
- 공개 Project를 조회할 수 있다.
- Post를 검색할 수 있다.
- Project를 검색할 수 있다.
- 로그인하지 않고 공개 콘텐츠를 읽을 수 있다.
- 댓글 및 좋아요 등의 회원 전용 기능에는 접근할 수 없다.

### USER

- Naver를 통해 로그인할 수 있다.
- 자신의 Post를 작성, 수정, 삭제할 수 있다.
- 개인 블로그 게시판을 만들고 최대 3단계까지 구성할 수 있다.
- 자신의 Post를 하나의 개인 게시판에 배치할 수 있다.
- 자신의 Project를 작성, 수정, 삭제할 수 있다.
- 코드 블록을 포함한 기술 콘텐츠를 작성할 수 있다.
- 코드 블록의 프로그래밍 언어를 지정할 수 있다.
- 다른 사용자의 공개 콘텐츠를 조회할 수 있다.
- 댓글을 작성하고 자신의 댓글을 관리할 수 있다.
- Post와 Project에 좋아요를 등록 및 취소할 수 있다.
- 탈퇴 예약을 7일 이내에 Naver 재인증으로 취소할 수 있고, 취소되지 않은 탈퇴 계정과 소유 데이터는 예정 시각에 파기된다.
- 미디어를 지정된 입력 한도 안에서 업로드할 수 있고, 원본이 보관되지 않으며 접근 URL이 15분 후 만료된다.
- 카테고리와 기술 태그를 이용해 콘텐츠를 탐색할 수 있다.

### MANAGER

- 관리자 계정으로 로그인할 수 있다.
- 사용자 목록을 조회할 수 있다.
- 사용자 상태를 관리할 수 있다.
- 사용자 Post를 검수할 수 있다.
- 사용자 Project를 검수할 수 있다.
- 콘텐츠를 차단 및 차단 해제할 수 있다.
- 콘텐츠를 강제 삭제할 수 있다.
- 댓글을 관리할 수 있다.
- 공통 카테고리와 기술 태그 목록을 관리할 수 있다.

### MASTER

- 관리자 시스템에 로그인할 수 있다.
- MANAGER 계정을 생성할 수 있다.
- MANAGER 계정을 활성화 또는 비활성화할 수 있다.
- MANAGER의 권한을 관리할 수 있다.
- MANAGER의 운영 기능을 사용할 수 있다.

### 공통

- HIDDEN 또는 관리자 차단 콘텐츠가 일반 사용자에게 노출되지 않는다.
- 삭제된 콘텐츠가 일반 조회 및 검색 결과에 노출되지 않는다.
- 사용자는 다른 사용자의 콘텐츠를 임의로 수정하거나 삭제할 수 없다.
- 관리자는 운영 목적의 콘텐츠 검수 및 제한을 수행할 수 있다.
- 역할에 맞지 않는 관리자 기능에 접근할 수 없다.
