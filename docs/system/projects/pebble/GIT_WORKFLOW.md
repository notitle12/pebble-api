# Pebble Git 작업 순서

이 문서는 pebble-api와 pebble-web에 공통 적용하는 Git 작업 기준이다. 각 저장소의 `AGENTS.md`와 영역별 개발 문서는 이 문서를 연결하며, 기존 사용자 변경과 이미 만들어진 커밋·PR·배포의 실제 상태는 보존한다.

## 기본 흐름

새 작업은 다음 순서로 진행한다.

1. 저장소의 현재 브랜치와 Git 상태, 기존 변경·커밋을 확인한다. 기존 작업을 덮어쓰거나 재작성하지 않는다.
2. 구현 전에 GitHub Issue를 만들거나 관련 Issue를 확인한다. 목적, 범위, 완료 조건, 필요한 검증을 적고 하나의 사용자 목표를 하나의 Issue·PR로 묶는다.
3. `dev`에서 분기한 작업 브랜치에서 변경한다. 브랜치 이름은 실제 Issue 번호를 포함해 `feature/<번호>-<요약>`, `fix/<번호>-<요약>`, `docs/<번호>-<요약>`, `chore/<번호>-<요약>` 중 작업에 맞는 접두사를 사용한다.
4. 변경과 필요한 검증을 마친 뒤 작업 브랜치를 원격에 push한다.
5. 관련 Issue를 연결한 PR을 `dev` 대상으로 연다. 변경 이유, 완료 조건, 실행한 검증과 결과, 미확인 범위를 사실대로 적는다.
6. PR 리뷰와 저장소에서 요구하는 CI·검사를 확인한다. 검토 의견과 실패를 해결하고, 필수 리뷰와 검사가 모두 충족된 뒤 PR을 통해 `dev`에 병합한다. 보호 규칙이나 필수 검사를 우회하지 않는다.
7. 완료 보고에는 Issue·브랜치·PR 링크, 병합 결과, 실제 검증 결과와 남은 제한을 기록한다. 아직 완료되지 않은 단계는 완료로 표현하지 않는다.

`main`은 릴리스 기준 브랜치다. 일반 작업 PR의 대상은 `dev`이며, `main` 반영은 검증된 릴리스 작업으로 진행한다. 배포는 이 흐름이나 PR 병합을 대신하지 않는다.

## 기존 작업과 초기 설정

이미 존재하는 변경, 커밋, 원격 브랜치, PR, 배포는 사실대로 보존한다. 작업 전에 만들어진 로컬 변경을 새 절차에 맞추려고 삭제·reset·rebase·강제 push하지 않는다. Issue가 나중에 생겼다면 Issue와 PR에 구현이 먼저 진행된 사실과 실제 날짜를 기록하며 과거 날짜를 바꾸거나 새 절차를 과거에도 지킨 것처럼 적지 않는다. 과거에 배포된 결과도 실제 배포 이력으로 기록하고 새 작업의 PR·CI·리뷰 절차를 대체한 것으로 간주하지 않는다.

최초 프로젝트 구성처럼 아직 원격과 `dev`가 없는 초기화 작업은 저장소 생성에 필요한 기준 브랜치 준비를 별도 초기 설정으로 기록한다. `dev`가 준비된 뒤의 작업은 기본 흐름을 따른다. 이미 완료된 초기화 이력을 다시 작성하지 않는다.

## 이슈와 검토 기준

Issue에는 해결하려는 문제, 포함·제외 범위, 완료 조건, 필요한 테스트나 문서 검증을 적는다. 구현 전 Issue가 원칙이며, 이미 착수된 경우에는 현재 사실을 투명하게 기록하고 가능한 다음 단계부터 흐름에 합류한다.

PR은 `dev`를 대상으로 열고 Issue를 연결한다. CI가 설정되지 않았거나 실행할 수 없으면 이를 명확히 적고, 저장소가 요구하는 필수 검토·검사를 충족하지 못한 상태로 병합하지 않는다. 리뷰나 CI 규칙을 우회해야만 진행 가능한 상태라면 완료로 보고하지 않고 차단 사유와 필요한 조치를 보고한다.

이 절차는 pebble-api와 pebble-web 모두에 적용한다. 언어·프레임워크별 구현 및 검증 명령은 각 영역 지침을 따른다.
