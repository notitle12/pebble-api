# Pebble 프론트엔드 상태와 데이터 수명

작성일: 2026-10-03. 설계 초안. 프론트에는 백엔드 DB 문서를 복제하기보다 어디에 어떤 상태를 보관할지 정하는 이 문서가 필요하다.

## 1. 상태 소유권

| 상태 | 저장·관리 위치 | 예 |
|---|---|---|
| 서버 데이터 | 기능별 조회 상태 또는 조회 캐시 | Post·Project·댓글·프로필 |
| 폼 입력 | 해당 폼 | 제목·블록·링크·파일 선택 |
| 탐색 조건 | URL query | q·tagId·page·sort |
| 일시 UI | 가까운 컴포넌트 | 열린 메뉴·모달·탭 |
| 인증 자격 | auth의 메모리 | Access Token |
| 인증 복구 단계 | auth | 확인 중·로그인·미인증·연결 실패 |
| 테마 같은 비민감 선호 | 필요한 경우 브라우저 저장소 | 테마·사이드바 설정 |

서버 데이터가 참조의 기준이다. 변경된 폼을 서버 캐시에 미리 섞지 않는다. localStorage를 사용할 수 있다는 것이 토큰·비밀 댓글·관리자 응답도 저장할 수 있다는 의미는 아니다.

## 2. 인증 복구 상태

시작 → 복구 중 → 인증됨 또는 미인증 또는 복구 실패로 구분한다. 확실한 refresh 인증 거부와 네트워크·서버 오류를 구분하고, 연결 실패를 무조건 로그아웃이나 Guest로 표시하지 않는다. 일시 오류에서도 이전 자격으로 보호된 쓰기를 임의로 성공 처리하지 않는다.

복구 중에는 개인정보·관리 메뉴를 잠시 대기 상태로 두며 공개 페이지는 읽을 수 있다. 확인된 미인증 상태에서 로그인 필요 안내를 제공한다. refresh의 상세 실패·재시도 제한은 [SECURITY](SECURITY.md)를 따른다.

## 3. 조회와 캐시

캐시를 도입하면 kind·리소스 ID·검색 조건·페이지·조회자 범위를 식별자에 포함한다. 조회자 범위는 세션 세대 또는 이미 받은 회원 ID로 구분하며 토큰 원문을 key나 로그에 넣지 않는다. 회원 ID도 개인과 연결되는 식별자이므로 비민감 정보로 단정하거나 불필요하게 외부 로그에 전송하지 않는다. USER와 관리자 캐시는 각각 분리한다.

- 로그인·로그아웃·계정 전환: 개인화된 콘텐츠·댓글·내 목록·프로필·관리자 캐시를 정리한다.
- 게시글 저장: 상세와 관련 내 목록·공개 목록을 갱신 또는 무효화한다.
- 댓글 변경: 대상 댓글 조회를 무효화한다.
- 좋아요 변경: 상세·이미 조회한 관련 목록의 likeCount·likedByMe를 서버에서 다시 확인한다.
- 차단·삭제·탈퇴: 공개 캐시·미디어 갱신 영향까지 확인한다. adminweb의 캐시 무효화만으로 다른 서비스의 CDN 캐시가 사라진다고 가정하지 않는다.

초기 설계에서는 공개 콘텐츠 응답의 장기 공유 캐시를 두지 않는다. 성능을 위해 도입할 때 TTL·이벤트 무효화·실패 시 오래된 내용 제공 여부를 정한다. SSR HTML·서버 fetch·CDN·브라우저 캐시는 다른 층이며 각각 검토한다. 개인 데이터와 관리자 응답은 공용 캐시하지 않는다.

## 4. 검색과 목록

검색어·필터 변경 시 첫 페이지로 이동하고 백엔드가 허용하는 query만 전송한다. 화면 1페이지는 API page=0이다. 이전 검색 요청의 늦은 응답이 최신 결과를 덮지 않도록 취소 또는 요청 식별자로 제어한다.

조회 캐시와 URL 상태를 연결하되 API가 없는 필터·월별 통계를 클라이언트의 현재 페이지 데이터로 흉내 내지 않는다. 검색 결과와 전체 통계는 구분한다.

## 5. 폼과 저장

서버 원본 → 편집 상태 → 입력 검증 → 저장 중 → 서버 성공 응답 반영 순으로 처리한다. 실패하면 입력을 보존한다. 저장 중 중복 제출을 막고 화면 이동 전 미저장 변경이 있을 때 안내한다.

PATCH는 누락·null·값 변경을 구분한다. 배열을 전송하면 전체 교체하므로 현재 편집 배열 전체를 보낸다. Project 주요 기능·링크 ID가 전체 교체 때 달라질 수 있어 기존 ID를 영구 UI 식별자로 가정하지 않는다. 임시 편집 key와 서버 ID의 역할을 구분한다.

콘텐츠 저장과 이미지 업로드는 별도 HTTP 요청일 수 있으며 둘을 하나의 원자적 저장처럼 설명하지 않는다. 콘텐츠 저장 후 업로드 실패라면 콘텐츠가 저장되었다는 사실과 미디어 재시도 경로를 표시한다. 권한·기한을 다시 확인한 명시적 재시도만 제공한다.

## 6. 낙관적 UI와 미디어

초기에는 저장·좋아요 결과를 확인한 뒤 UI에 반영하는 방식을 기본 제안한다. 낙관적 업데이트는 서버 성공 전에 화면을 바꾸는 방식이며 실패 복구·경합 처리가 필요하다. 복잡성을 감수할 이유가 생기면 해당 기능에서 검토한다.

signed URL은 영구 데이터가 아니다. API가 반환한 URL을 사용하고 만료 또는 접근 실패 시 권한을 통과하는 콘텐츠 조회로 갱신한다. URL이 null이면 임의 키·주소를 만들지 않는다. 같은 이미지 오류에 무한 재조회하지 않는다. 업로드 미리보기 object URL은 파일 교체·화면 해제 때 정리한다.

## 7. 상태 검증 시나리오

빠른 연속 검색, 뒤로 가기, 새로고침, 로그인 전후 likedByMe, 계정 전환 후 SECRET 댓글, 저장 실패 입력 보존, 저장과 업로드의 부분 실패, 만료 이미지 URL, 동시 좋아요 클릭을 확인한다. refresh 경합은 인증 검증 시나리오와 함께 수행한다.
