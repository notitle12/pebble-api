# Pebble 프론트엔드 개발과 검증

작성일: 2026-10-03. 공통 원칙과 프로젝트 계약을 실제 작업에 적용하는 절차다.

## 1. 읽기 순서

[공통 AGENTS](../../../AGENTS.md) → 공통 개발·프론트 기준 → 이 폴더 README → 현재 작업 문서 순으로 읽는다. 프론트 작업마다 DB·백엔드 구현 전체를 읽지 않고, 인증·API·데이터 계약에 관련된 절만 확인한다.

web의 설치된 Next.js 지침은 루트 AGENTS.md와 node_modules/next/dist/docs를 따른다. adminweb은 실제 저장소 지침·package scripts·프레임워크를 확인한다. 새 원칙은 공통 또는 프로젝트 문서 중 맞는 곳에 추가하고 루트 AGENTS에 장문을 복제하지 않는다.

## 2. 현재 확인된 환경

| 항목 | web 현재 상태 |
|---|---|
| 프레임워크 | Next.js 16.3.8, React 19.3.0 |
| 언어·런타임 | TypeScript 7.0.2, Node >=22 <23 |
| scripts | dev, build, start, typecheck, test, dev:mock |
| src | app + features/post/api·components |
| 실제 페이지 | / 공개 게시글 목록 (Issue #2 작업 브랜치) |
| API·로그인 구현 | Guest 공개 목록 조회 구현, 로그인 미구현 |
| 테스트 명령 | npm test: Node 기본 테스트 21개 |
| next.config | poweredByHeader:false, 배포 adapter·API proxy 설정 없음 |

버전·script는 작업 시 package.json과 lockfile을 확인한다. 기존 문서의 이전 초안 테스트·실연동 기록을 현재 코드의 결과로 재사용하지 않는다. Issue #2 작업에서 테스트·타입 검사·빌드를 실행해 통과했다. 상세 검증 범위는 README와 source/PUBLIC_POST_LIST.md를 따른다.

## 3. 작업 단위

하나의 사용자 행동을 목표로 정한다. 예: 공개 글 상세를 읽고 없는 글의 404와 API 연결 실패를 구분한다. 페이지별로 UI만 먼저 완료했다고 기록하지 않고 데이터·입력·상태·권한·검증을 함께 묶는다.

작업 전 목적, 사용 API, 화면 상태, 변경 파일 범위, 검증 방법을 확인한다. 기존 시안은 참고이며 실제 데이터가 없는 요소를 가짜로 구현하지 않는다. 관련 계약 차이는 [DECISIONS](DECISIONS.md)에 기록한다.

## 4. Git과 기존 문서

[공유 Git 작업 순서](../GIT_WORKFLOW.md)와 현재 원격·브랜치·Issue 상태를 우선 확인한다. Issue를 먼저 확인하고 `dev`에서 실제 Issue 번호가 포함된 브랜치를 만들어 작업한 뒤 push와 `dev` 대상 PR, 필수 검토·CI, PR 병합을 순서대로 진행한다. 기존 사용자 변경과 과거 작업 기록은 보존하며 실제로 완료하지 않은 단계를 완료로 적지 않는다.

기존 GUIDELINES의 npm test·초기 원격 미연결 같은 문구는 현재 package.json·Git 상태와 대조한다. 과거 기록을 조용히 현재 사실로 바꾸지 않는다. 상충하는 계약은 근거·영향을 확인하고 결정한 변경을 기록한다.

## 5. 검증 선택

현재 web에서 가능한 검증 명령은 npm test, npm run typecheck, npm run build다. 기능 테스트가 필요하면 실제 행동을 검증하는 환경과 script를 해당 작업에서 추가한다. 문서 작성만을 위해 dependency나 테스트 도구를 설치하지 않는다.

| 변경 | 검증 |
|---|---|
| 문서 | 상대 링크·원본 연결·읽기 순서·계약 대조 |
| 순수 UI | 타입 검사·실제 렌더링·모바일·키보드·빈/오류 상태 |
| 데이터 조회 | 응답·오류 처리, 취소·검색 경합·페이지 경계 |
| 저장 폼 | 입력 보존·중복 제출·부분 실패·PATCH 생략/null |
| 인증 | SECURITY의 동시성·쿠키·실제 OAuth 시나리오 |
| 공개 SSR | 첫 HTML 본문·메타데이터·404·개인 데이터 유출·캐시 |
| 배포 | Workers 실제 preview·런타임·도메인·Origin·회귀 |

작은 변경은 관련 검증으로 충분하며 동일 성공 검증을 이유 없이 반복하지 않는다. 빌드 통과는 인증·배포·브라우저 성공이 아니다. 실패한 테스트를 삭제·비활성화하지 않는다.

## 6. 화면 품질

정상·로딩·빈·실패·권한·저장 중 상태, 긴 한글 제목·코드·태그·handle, 좁은 화면, 메뉴 focus·Escape·복귀, 이미지 실패와 대체 텍스트를 확인한다. 공개 색·간격은 기존 DESIGN의 초안이며 실제 대비·레이아웃 검증을 대신하지 않는다.

## 7. 인계

완료 기능과 코드 범위, 실제 실행한 명령·환경·결과, 실제 API·OAuth·브라우저 검증 여부, 기준 브랜치와 남은 계약·시안·배포 문제를 짧게 남긴다. 날짜 기준 구현 상태는 README에, 새 판단은 DECISIONS에, 계약은 해당 원본에 갱신한다.
